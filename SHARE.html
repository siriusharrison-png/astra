01

What it is

A foundation an agent loads before it works

Instead of re-explaining your rules, your preferred component names, and your working style every session, you keep them in one place the agent reads first. It is a base of rules, structure, language, and decision logic — the things you reuse across every project — so different tools and sessions all start from the same ground.

A local operating base for design-support work, designed to keep repeated thinking consistent across tools, projects, and sessions.

01 — What it is

What it is not

  • Not a feature product, and not something end-users touch.
  • Not a knowledge dump — content earns its place only if it's reusable across projects.
  • Not a homepage or a showcase. It is infrastructure, loaded silently before work.

What it changes

Value where ambiguity, precision, and repetition live

Astra is not free value on every task. For a small, unambiguous, one-off request it adds little. It shows up in three situations — and the without side isn't a strawman, it's how a capable agent actually behaves by default.

02 — What it changes

The pattern

Without a foundation, each task starts from zero and each word is taken at face value; with one, tasks start framed, words are made precise, and lessons persist. The return scales with ambiguity, precision-sensitivity, and repetition — and is near-zero without them. Use it where it pays.
03

Build your own

You don't need this repo — you need these decisions

If the idea fits how you work, build your own. The specific files matter far less than the five aspects next.

Aspect 01 / 05

Layer by stability, not by topic

  • Stable — what the base is and how it's used. Changes rarely and deliberately.
  • Evolving — recurring patterns and validated lessons. Updated after tasks.
  • Working — task-scoped drafts. Rewritten freely, never permanent.

Daily churn should never destabilize your core rules. One undifferentiated pile either goes stale or becomes too risky to touch.

Aspect 02 / 05

Make methods the hook, keep data on demand

Load the method every session; load the data only when needed. A rule like “name UI elements with their standard component names” is small and always worth loading — the 62-entry lookup table it points to is not. Separating the trigger from the payload is what keeps the base from bloating.

Aspect 03 / 05

Capture only what's reusable — and deliberately

The failure mode of any knowledge base is the junk drawer. Two guards: a reusability bar (if a lesson only helps one task, it dies in the working layer) and confirm before writing (propose what to capture, write only after a human agrees). Silence is the correct default.

Aspect 04 / 05

One source of truth, synced — not copied

Keep the canonical copy in one place; machines read a local copy and updates flow through sync. The moment the same rule exists in two hand-copied places, they drift and you can't trust either.

Aspect 05 / 05

Pick one working language and stay in it

Its whole job is to keep wording stable so behavior is stable. Mixed or drifting vocabulary quietly reintroduces the ambiguity the base exists to remove.

The takeaway

Discipline, not content

The value isn't the content — it's the discipline: layer by stability, hook methods to data, capture deliberately, sync from one source. Get those right and the foundation stays small, trustworthy, and genuinely reusable. Get them wrong and you've built another folder of documents nobody loads.
